# Product hardening — acceptance contract, 14 November 2026

The implementation follows the whole-product CLI audit. Preserve the accepted
brand/hero, all legitimate routes, tools, content and user data. An unavailable
provider must remain a recoverable state, never a fabricated success. No desktop
control, external message, purchase or market order is part of these tests.

## Cycle 1: truthful execution and a usable learner client

- Registry, HTTP and MCP resolve supported pricing tools to real engines with
  matching units, inputs and methodology; unsupported contracts stay discoverable
  with explicit capability status and nonzero CLI exits, never a successful fake
  price. Descriptor coverage and executable coverage are separate measurements.
- RFQ futures use Black-76; a bounded, actually executed autocall Monte Carlo
  states its GBM assumptions, observation schedule, seed and uncertainty. It must
  preserve the underlying and horizon. No claim of calibrated local/stochastic
  volatility, live data, correlation risk or limit approval without that evidence.
- The offline assistant preserves explicit parameters and requested language.
- Signed dashboard requests wait for their token; the dashboard projects real
  Interview activity without changing historical course scores. Refresh/retry,
  another account and exact resume are tested.
- Forms have accessible names; active text contrasts meet the applicable WCAG
  threshold; titles track resolved route state; keyboard focus remains usable.
  A display equation that overflows at a small width is focusable and actually
  scrolls with the keyboard, without changing the equation or course content.
- A signed `tpl` client exposes named actions, JSON contracts, stable exit codes,
  timeouts, private exports and idempotency. Secrets come from environment or a
  private file. An operator key is not a substitute for a learner identity.
- Each current feature has a coverage row identifying command, real capability,
  permissions, normal/error/resume evidence, or an external dependency. Counting
  descriptors, routes or test lines is not a claim of 100% functional coverage.

## Cycle 2: a coherent preparation workflow and portable work

- A generated exercise can retain an immutable written attempt, then disclose its
  worked correction and save a self-review. Do not invent automatic grades for
  free-text reasoning. Cross-owner access is denied and duplicate requests are
  idempotent. Existing saved exercises remain readable and unchanged.
- Survival has the same question bank and rules in API, CLI and UI: 20 questions,
  30 seconds per question, three lives, feedback preserved until Next. Scoring is
  server-calculated, but practice remains unproctored and unranked. Reload resumes
  the same question/feedback, rather than resetting the timer to improve a score.
- The barrier challenge opens its original ticket and a real runnable starter.
  Both registered notebooks export valid `.ipynb` and `.py`; a CDN failure leaves
  a local Python route. The server executes allowlisted examples only, never
  arbitrary uploaded code.
- Course generation respects the requested language. The original French library
  remains accessible with its language stated before entry. Any English programme
  must have actual English lessons, equations, verified exercises and appropriate
  sources; no translated label over French prose or arbitrary mastery score.
- Case reports, reproducible files, a small Anki deck and voluntary study-calendar
  export retain conventions and original content. Downloads do not count as use
  in Excel/Anki or attendance. Learner history is private by default.

## Cycle 3: release and independent review

Run targeted meaningful tests after each implementation batch, then the relevant
regression and CLI/headless journeys. Technical RL and the independent Business
Client Mystère reviewer return separate verdicts; a trust blocker prevents PASS
regardless of numerical reviewer score. Record tested commits and push paired
checkpoints. Never publish corpus, full licensed scripts, screenshots of private
lessons, databases, tokens or environment files.

The existing mobile performance gate retains its Pixel 5, 1.6 Mbps / 750 kbps,
150 ms RTT and 4x CPU profile: FCP ≤2500 ms, LCP ≤4000 ms, CLS ≤0.1, three
observed interactions with median ≤300 ms and maximum ≤400 ms. Loading-order
fixes must be verified against the generated artifact and the unchanged gate;
do not reinterpret initial failures as passes or lower the thresholds.

Commercial infrastructure, legal identity, source rights, real support, Stripe,
Supabase email, public deployment and pilot purchase evidence require their own
proof. Build and exercise their configuration/acceptance paths; never invent
credentials or mark these conditions satisfied from local fixtures.
